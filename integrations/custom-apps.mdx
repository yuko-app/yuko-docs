## Introduction

A **custom app** is an OAuth 2.0 client registered with Yuko. It lets an external tool (a checkout provider, a partner app or your own internal system) ask a merchant for access to their Yuko data, instead of the merchant copying a REST API key by hand.

Once the merchant approves, the app receives an access token and calls the [REST API](/integrations/rest-api) with the scopes the merchant granted.

<Info>Custom Apps don't push Yuko events to other tools. To receive events, use [Webhooks](/integrations/webhooks). To call the API from a single store's systems, a [REST API](/integrations/rest-api) key is simpler.</Info>

## When to use

- You're building an app that many Yuko merchants will connect to.
- You want merchants to connect with one click and approve access, rather than paste an API key.
- You need tokens that can be revoked without affecting the merchant's other keys.

## What a custom app includes

| Setting | What it is |
|---|---|
| **App name** and **Description** | Shown to the merchant on the approval screen. |
| **Redirect URL (Callback)** | Where Yuko sends the merchant after they approve or deny access. |
| **Installation URL** and **Settings URL** | Your app's install and settings pages. |
| **Client ID** and **Client Secret** | The app's OAuth credentials. Keep the secret on your server. |
| **API Scopes** | The access the app requests: **Custom**, **Read-Only** (read access for all scopes) or **Full Access** (read/write access for all scopes). With **Custom**, set each resource to **None**, **Read** or **Read/Write**. See [Scopes](/developer/api/scopes). |

## How the connection works

<Steps>
  <Step title="Your app sends the merchant to Yuko">
    The app redirects the merchant to Yuko's authorisation page with its client ID, redirect URL, requested scopes and a `state` value.
  </Step>
  <Step title="The merchant approves">
    Yuko shows the app's name and the access it's asking for. The merchant clicks **Authorize** or **Deny**.
  </Step>
  <Step title="Your app exchanges the code">
    Yuko redirects back to the app's redirect URL with an authorisation code. The app's server exchanges the code for an access token and a refresh token.
  </Step>
  <Step title="Your app calls the API">
    The app sends the access token as a Bearer token on [REST API](/developer/api/introduction) requests, within the approved scopes.
  </Step>
</Steps>

## Best practices

<Tip>**Request only the scopes you need.** Merchants are more likely to approve narrow access.</Tip>
<Tip>**Keep the client secret and tokens on your server.** Never put them in browser or mobile code.</Tip>
<Tip>**Test with a development store** before asking real merchants to connect.</Tip>

## FAQs

<AccordionGroup>
  <Accordion title="What's the difference between a custom app and a REST API key?">
    A REST API key is created by the merchant in **Integrations → REST API** and pasted into your tool. A custom app uses OAuth, so the merchant approves access from your app without handling keys.
  </Accordion>
  <Accordion title="What's the difference vs Webhooks?">
    Custom apps call Yuko's API. Webhooks send Yuko events to your server. Many integrations use both.
  </Accordion>
</AccordionGroup>
